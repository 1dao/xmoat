# 指标口径

每个数字从哪里来、怎么算、什么时候算不出来。实现分别在 `engine/` 下对应的文件里，
测试用例在 [test/unit.lua](../test/unit.lua)，大多附有手算过程。

## 数据源字段

来源是东方财富公开接口，字段映射集中在 [engine/source_em.lua](../engine/source_em.lua)。

| 数据集 | 接口 | 用途 |
|---|---|---|
| 主要财务指标（按报告期） | `RPT_F10_FINANCE_MAINFINADATA` | 营收、利润、ROE、ROIC、毛利率、负债率、银行指标 |
| 每日估值 | `RPT_VALUEANALYSIS_DET` | 收盘价、市值、PE(TTM)、PB(MRQ)、PS(TTM)、PCF(TTM) |
| 分红送配 | `RPT_SHAREBONUS_DET` | 每股派现、除息日、方案进度 |
| 资产负债表 | F10 `zcfzbAjaxNew` | 货币资金、应收、存货、商誉、借款（仅一般企业） |
| 日线行情 | `push2his` `stock/kline/get` | 开高低收、成交量额、换手率；技术面与筹码分布的全部输入 |
| 日线行情（批量） | 通达信行情协议（TCP 7709） | 全市场扫描用：二进制、长连接、一次 800 根，见下 |

单位约定：金额为元；ROE、利润率、负债率、增速为百分数（15.2 表示 15.2%）；
经营现金流 / 净利润是倍数（1.53 表示 153%）；每股派现为元/股（源数据是每 10 股，已除以 10）。

## 两个容易出错的地方

**累计值。** 一季报、中报、三季报里的营收和利润是年初至今的累计数，不是单季。
中报利润不能直接和年报比，四个累计数也不能相加。

**报告期和公告日。** 2025 年三季报的报告期是 9 月 30 日，市场 10 月底才看到。每期报告都保存了公告日
（`notice_date`）。历史估值直接用数据源每日计算的值，而不是用今天看到的报告回算过去，
这样不会把事后才公布、甚至事后追溯调整的数字带进过去的日期。

## TTM（近十二个月）

```
最新是年报：  TTM = 年报值
否则：        TTM = 最新累计 + 上一年年报 − 上年同期累计
```

例：2025 中报累计 50，2024 年报 100，2024 中报累计 40 → TTM = 110。
缺任何一期就不算，并在结果里说明缺哪一期。

## 估值分位

- 窗口：全部历史（数据源从 2018 年起）和近 5 年。
- 只统计正值。PE 为负表示亏损，不代表便宜；把亏损期放进样本，会让盈利年份看起来都偏贵。当前值为负时不给分位。
- 分位 = (低于当前值的天数 + 等于当前值的天数 / 2) / 样本天数 × 100。当前这一天本身也在样本里。
- 样本少于 240 个交易日（约一年）时不给分位。

## 反向 DCF

给定现价，反推市场隐含的增长率：

```
价值(g) = Σ(t=1..n) E(1+g)^t / (1+r)^t  +  E(1+g)^n (1+tg) / (r − tg) / (1+r)^n
求 g，使 价值(g) = 总市值
```

- E = 归母净利润（TTM），近似股东盈余。需要大量再投资才能增长的公司，真实可分配的现金更少，
  所以隐含增长率应当看作下限。
- r、tg、n 取自配置 `DCF_DISCOUNT_RATE`（默认 10%）、`DCF_TERMINAL_GROWTH`（3%）、`DCF_YEARS`（10 年），
  每个结果旁边都会显示。
- 用二分法在 −50% 到 100% 之间求解；超出范围时标注"低于"或"高于"。
- E ≤ 0 时不计算。

## 股息率与分红

- **股息率（近 12 个月）**：除息日落在最近 365 天内的每股派现合计 ÷ 最新收盘价。按除息日而不是报告期统计，
  因为股息率说的是持有人过去一年实际收到了多少。
- **年度分红**：按报告期所属年度汇总（中期和年末合计），分红率 = 年度每股派现 ÷ 当年年报基本每股收益。
- **连续分红年数**：从最近一个年报的年度往回数，遇到没有分红的年度就停。不从"最近一次分过红的年度"开始数，
  否则停止分红的公司看起来仍然连续。
- 方案进度为"停止实施""股东大会否决""不分配"的不计入；已宣布、尚未股东大会通过的方案计入对应年度，
  但在除息之前不计入股息率。

## 经营质量（年报）

只用年报，最多近 10 年。汇总项：

| 项 | 口径 |
|---|---|
| ROE 均值 / 最低 | 近 5 个年报的加权 ROE |
| ROIC 均值 | 近 5 个年报（一般企业） |
| 毛利率均值、波动幅度 | 近 5 个年报；波动幅度 = 最高 − 最低 |
| 经营现金流 / 净利润 均值 | 近 3 个年报 |
| 营收、归母净利润复合增速 | 最多近 6 个年报的首尾，标注实际跨度；首尾任一为负不计算 |

## 检查清单

每项结果为 通过 / 注意 / 数据不足。**数据不足不等于通过。** 阈值集中在
[engine/checks.lua](../engine/checks.lua) 顶部，也可以通过 `system.info` 取到。

**一般企业**

| 检查 | 提示条件 |
|---|---|
| 最近一个财年盈利 | 年报归母净利润 ≤ 0 |
| 利润有现金流支撑 | 近 3 个年报 经营现金流 / 净利润 均值 < 0.8 |
| 利润主要来自主业 | 扣非净利润 / 归母净利润 < 80% |
| 毛利率没有明显下滑 | 同比下降超过 5 个百分点 |
| 应收账款没有远快于营收 | 应收同比增速 − 营收同比增速 > 20pt，且应收 ≥ 营收的 5% |
| 存货没有远快于营收 | 存货同比增速 − 营收同比增速 > 30pt，且存货 ≥ 营收的 10% |
| 商誉占净资产比例不高 | 商誉 / 归母净资产 > 30% |
| 没有"存贷双高" | 货币资金 / 总资产 ≥ 15% 且 有息负债 / 总资产 ≥ 15% |
| 现金能覆盖短期有息负债 | 货币资金 < 短期借款 + 一年内到期的非流动负债 |
| 资产负债率不高 | 最新报告资产负债率 > 70% |

有息负债 = 短期借款 + 长期借款 + 应付债券 + 一年内到期的非流动负债。这是近似值：
不含租赁负债，而"一年内到期的非流动负债"里可能有不计息的项目。

**银行**

| 检查 | 提示条件 |
|---|---|
| 最近一个财年盈利 | 同上 |
| 不良贷款率不高 | 最新 > 2% |
| 不良率没有上升 | 最近两个年报之间上升超过 0.1 个百分点 |
| 拨备覆盖率充足 | 最新 < 150% |
| 核心一级资本充足 | 最新 < 8.5% |

**保险**

寿险的利润受投资市场和准备金假设影响很大，所以看的是另一套。点值型指标（偿付能力、内含价值）取最新一期报告；
流量型指标（退保率、投资收益率）只取年报，因为中报口径是半年，直接比会误判。

| 检查 | 提示条件 |
|---|---|
| 最近一个财年盈利 | 同上 |
| 偿付能力充足 | 综合偿付能力充足率 < 150%（监管红线 100%，150% 是监管关注线） |
| 新业务价值没有明显下滑 | 最近两个年报之间下降超过 10% |
| 退保率不高 | 年报退保率 > 3% |
| 净投资收益率不低 | 年报净投资收益率 < 3.5%（长期定价假设通常在 4%–5%） |

估值上另外给出 **P/EV = 总市值 / 内含价值**，取最新一期报告的内含价值。内含价值是保险公司按自己的精算假设算的，
假设调整后口径会变，不同公司之间也不完全可比。

**证券**

用的全是监管在《证券公司风险控制指标管理办法》里定义、公司自己披露的风控指标。每项都有监管红线和预警线，
这里用**预警线**，也就是在触及红线之前就提示。全部是点值型，取最新一期报告。

| 检查 | 提示条件 | 监管红线 |
|---|---|---|
| 风险覆盖率充足 | < 120% | 100% |
| 资本杠杆率充足 | < 9.6% | 8% |
| 流动性覆盖率充足 | < 120% | 100% |
| 净稳定资金率充足 | < 120% | 100% |
| 净资本占净资产比例充足 | < 24% | 20% |
| 自营权益敞口不高 | > 80% | 100% |

**其他类型**：没有专门模板的公司只有盈利检查，分析结果里会说明。

## 点位（买入 / 止损 / 目标）

实现在 [engine/levels.lua](../engine/levels.lua)。全部是规则算出来的，**不是建议**，
而且换一组假设就是另一组数字——每个数字都带着自己的依据字符串。

**估值锚。** 把一个倍数换算成价格：

    某倍数 m 对应的价格 = 当前收盘价 × m ÷ 当前倍数

这等于把分母（TTM 盈利、每股净资产）固定在今天的水平。它准确回答的是
「回到历史中位 PE 对应多少钱」，它不能回答「明年值多少钱」：下一份财报公布后，同样的分位对应另一个价格。

用哪个倍数：银行、保险、券商用 PB，其余用 PE(TTM)；如果你给这只股票设了合理区间，就用区间的那个指标。
PS 和 PCF 不作为锚——没有利润率假设的市销率说明不了一股值多少钱。

| 点位 | 默认算法 | 设了合理区间时 |
|---|---|---|
| 买入区间 | 倍数回到全历史 10%–25% 分位对应的价格 | 区间下沿对应的价格；下沿比 10% 分位还低时只给一个「以下」价 |
| 目标价 | 倍数回到全历史 70% 分位 | 区间上沿对应的价格 |
| 止损价 | 现价下方最近的支撑 × (1 − 3%) | 同左，止损与估值区间无关 |
| 盈亏比 | (目标价 − 现价) / (现价 − 止损价) | 同左 |

支撑按这个顺序找现价**下方**最近的一条：MA250、MA120、MA60、筹码 90% 下沿、近 250 日最低；
都在现价上方（价格已经跌破全部均线）时退回近 250 日最低。缓冲 3% 是因为人人都看得见的位置会先被击穿再站住。

分位、缓冲都在 `xmoat.cfg` 里（`LEVEL_*`）。指标为负（亏损、净资产为负）或历史样本不足 240 个交易日时，
这一整块不出数，只给原因。

**对长期持有者的提醒**（输出里也有）：真正该让你卖出的是基本面变坏，不是价格跌到某个数字。
这里的止损价只是一条机械的风险线。

## 技术面

实现在 [engine/tech.lua](../engine/tech.lua)，输入是本地缓存的日线（前复权，
[engine/quote.lua](../engine/quote.lua)），只算不判断：它回答价格在什么位置，不回答公司值不值得买。

**前复权。** 指标都算在前复权价上，否则除权那天的跳空会被当成一次真实的下跌。
代价是分红会改写整段历史价格，所以增量抓取时会重叠十天做校验，对不上就整段重抓。

**均线（MA）** 是最近 n 个交易日收盘价的算术平均，n 取 5、10、20、60、120、250。
不足 n 天就没有这条均线，不用更短的天数凑。

**多头排列 / 空头排列。** MA5 > MA10 > MA20 > MA60 且收盘价在 MA5 之上是多头排列，
全部反过来是空头排列，其余一律是「未形成排列」——不把中间状态硬凑成一个结论。
另外给出收盘价站上了几条均线（`above_ma` / `ma_count`）。

**乖离率（BIAS）** = (收盘价 − MAn) / MAn × 100%，n 取 6、12、24、60。
它衡量的是价格离自己的均线有多远，这个距离本身是均值回复的。

**位置** 取近 250 个和近 60 个交易日的最高价与最低价：`position` 是收盘价在这个区间里的百分位
（0 为区间最低，100 为最高），`from_high` 是相对最高价的涨跌幅（负数表示离高点还有多远）。

**量能** = 近 5 日平均成交量 / 近 60 日平均成交量。大于 1 表示最近放量。

### 筹码分布

没有人公布谁在什么价位持有一只股票，所以这是**估算模型**，不是真实持仓。做法是标准的换手衰减法：
从最近 500 个交易日开始，逐日把当天的换手率 t 视为「这部分流通股换了手」——

1. 已有的全部筹码乘以 (1 − t)，即衰减掉被换手的那一部分；
2. 把权重 t 按三角分布撒在当天的价格区间 [最低价, 最高价] 上，峰值落在当天均价
   （成交额 ÷ 成交量，异常时退回 (高 + 低 + 2 × 收) / 4）。

价格轴切成 200 个桶。由此得到：

| 指标 | 定义 |
|---|---|
| 平均成本 | 各价位按筹码权重的加权平均 |
| 获利比例 | 成本低于等于最新收盘价的筹码占比 |
| 90% / 70% 成本区间 | 权重从低到高累计到 5%–95% / 15%–85% 的价格区间 |
| 集中度 | (区间上沿 − 区间下沿) / (上沿 + 下沿) × 100%，越小说明筹码越集中 |

**模型的假设，也就是它的边界：** 换手率来自流通股口径，限售股解禁、大宗交易和同一批筹码反复换手
都会让它失真；衰减系数默认 1（当天换手率就是被替换的比例）；指数没有换手率，所以没有筹码分布。
换手率数据不足 60 天时直接不给结果，而不是拿短样本硬算。

## 主营构成

来自东方财富 F10 的经营分析（`BusinessAnalysis/PageAjax`），按行业、产品、地区三种口径。
源数据里的占比和毛利率是小数（0.8569），这里统一换算成百分数。

只取**最近一个年报**：中报的产品结构受季节影响，和年报混在一起看不出趋势。占比变化是同一条目
相对上一年年报的百分点差，由程序计算好，不让模型去做减法。

同一份接口还返回**管理层经营评述**，但只有最新一期。每次刷新都会把当期评述存下来（最多 8 期），
所以跟踪一年之后就有两期年报的评述可以对比。

## 横盘之后上穿均线

实现在 [engine/backtest.lua](../engine/backtest.lua)（`breakout` 信号）与
[engine/strategy.lua](../engine/strategy.lua)（多股票拟合与扫描）。规则两句话：

1. **横盘**：今天之前的 `flat_lookback` 个交易日里，最高价比最低价高出不超过 `flat_max`%——
   股价真的挤在一个窄区间里；
2. **上穿均线**：昨天收盘不高于 n 日均线 × (1 + `above_pct`%)，今天收盘高于它。
   可另外要求当天涨幅 ≥ `min_day_gain`%；
3. **个股月线向上**（`month_up`）：收盘在最近 10 个已经走完的月份的收盘均值之上，且这条均线比 3 个月前高。
   当月还没走完，它的收盘在那一天是个未来的价格，所以不算。

另有一个大盘开关（`bull_only`）：沪深300 不在多头（和复盘同一个定义）的日子，信号照常列出和记录，
但不推送。

默认值在 `xmoat.cfg` 的 `BREAKOUT_*`：**横盘 8 周（40 日）、振幅 ≤ 10%，收盘上穿 10 周（50 日）均线，
个股月线向上；沪深300 不在多头时不推送**。前两条是规则本来的意思，后两条来自下面周线、月线的对比。

**横盘量的是股价，不是均线。** 第一版的「横盘」是「40 日均线在 5 周里变动不超过 1%」，
可股价在均线两侧来回 20% 时，均线照样首尾持平：海安集团 2026-09-21 被选中时，40 日均线 5 周只变了 0.4%，
股价前 40 天的最高价比最低价高 22%，当天收盘也没过这段时间的最高点。那一版还只要求「收盘高出均线 3%」，
不要求当天上穿，于是一只已经在均线上方待了一周的股票也算「突破」。

**回测结果（全市场、2021–2026、持有 60 个交易日，逐年和同一年随便哪天买比，单位百分点）**：

| 规则 | 信号 | 胜率 | 超额（5 年） | 2022 | 2023 | 2024 | 2025 | 2026 上半年 |
|---|---|---|---|---|---|---|---|---|
| 旧：40 日均线走平 5 周 + 高出 3% | 41593 | 45% | **−1.6** | −2.6 | −2.8 | −1.0 | −0.3 | −1.0 |
| **现：横盘 8 周 ≤10% + 上穿 10 周线** | 4257 | 49% | **+0.4** | −1.3 | +2.3 | +7.6 | −2.0 | +4.7 |
| 横盘 10 周 ≤10% + 上穿 10 周线 | 1840 | 47% | +0.2 | −1.8 | +3.4 | +5.7 | −3.5 | +5.6 |
| 横盘 8 周 ≤10% + 高出 10 周线 3% | 3775 | 48% | +0.2 | −2.3 | +1.4 | +5.0 | −2.6 | +3.2 |
| 横盘 8 周 ≤10% + 收盘越过箱顶 | 3166 | 47% | +0.0 | −2.9 | +1.2 | +4.8 | −3.1 | +3.7 |

**读法**：比旧定义好了约 2 个点，但只是和随便哪天买差不多——胜率持平，5 年里 2 年为负，
其中 2025 年恰是信号最多的一年；持有 20 天时各个版本都略跑输。几个变体之间的差别都在噪声里，
所以没有在同一批数据上继续调参。**这不是一条被证明有效的规则**，信号记录（下面）是往后的检验。

**这些数字怎么来的，以及之前错在哪。** 每只股票用通达信拉满 1200 个交易日（`strategy.prefetch`
加 `force`，约两分钟、1 GB），信号和基准都按年份分开比。两件事会让结果看起来比实际好：

- **日线太短**。之前写在这里的「40 日均线 + 3%，60 日超额 +2.6 个百分点、胜率高 7 个点，五年」，
  用的缓存大多只有约 400 个交易日；报告里的「2021 起」是**最早那只股票**的起始日。网格报告现在会写出
  每只股票日线的中位长度和多数股票的起始日，短缓存不会再被读成五年。同一条规则在真正的五年上是 −1.6。
- **只看合计**。信号在不同行情里出现得多少不一样，把几年合在一起和一个合在一起的基准比，
  会把「这段时间整体涨了」算成规则的功劳。逐年（或逐半年）比才公平。

**参照周线和月线：9 条规则的对比。** 同一套方法（全市场、持有 60 个交易日、和同一个半年里随便哪天买比胜率），
把 5 年分成「发现」（2021–2023）和「检验」（2024–2026）两段——测的规则越多，越容易撞上一条碰巧好看的，
两段都成立才算数。周线、月线的规则在那一周（月）的最后一个交易日收盘判断，月线只用走完的月份：

| 规则 | 信号 | 胜率超额 | 2021–23 | 2024–26 | 半年里为正 |
|---|---|---|---|---|---|
| 周线多头排列形成 | 51013 | **−4.1** | −7.8 | −2.7 | 1/9 |
| 周线创 26 周新高 | 41632 | **−4.8** | −7.8 | −5.0 | 2/9 |
| 周线创 52 周新高 | 26018 | **−5.5** | −9.7 | −6.7 | 2/8 |
| 月线向上 + 周线上穿 10 周线 | 30185 | +0.8 | −4.4 | +0.7 | 3/8 |
| 周线 MACD 零轴上金叉 | 16950 | −0.6 | −5.6 | −0.8 | 2/9 |
| 月线向上 + 回踩 20 周线 | 34849 | +1.6 | −2.7 | +1.4 | 4/8 |
| 横盘 8 周 ≤10% + 上穿 10 周线 | 4401 | +0.2 | −2.2 | +2.3 | 5/10 |
| **同上 + 个股月线向上（现在的规则）** | 1210 | **+3.2** | **+5.4** | **+0.7** | 5/7 |

- **追周线强势，两段都跑输**：多头排列形成、创 26 周或 52 周新高，胜率比随便哪天买低 4 到 5.5 个点，
  持有 120 天也一样。这 5 年的 A 股里，看见周线走强就追是系统性地差——别再把它当候选。
- **加上个股月线向上，是唯一两段都为正的组合**，但优势在变小（+5.4 → +0.7），持有 120 天时不成立，
  信号也少七成。它进了默认规则，说明文字如实写着这些。
- **大盘多头时**：横盘突破比同样日子随便买高 4.1 个点，「月线向上 + 回踩 20 周线」持有 120 天高 3.6、4 个半年全为正——
  但沪深300 的多头只出现在 2024–26 这一段，没有第二段可以检验，所以只做成推送开关。

**剔除负市盈率、要求当天大涨，都不能让它更好**（同一套方法）：要求当天至少涨 3%，两段都更差
（−3.7 / −1.2，对比不加的 −2.2 / −0.4，这里用的是旧定义）；只看盈利公司，前一段好一点、后一段反而差一点，
没有稳定的方向。

**信号是上穿的那一天。** 之后 `BACKTEST_COOLDOWN`（20）个交易日内同一只不再算，
免得在均线附近来回穿的股票一个月里算成好几次突破。扫描的「最近 N 个交易日」找的是这段时间里上穿的，
并给出信号日以来涨了多少。

**信号记录**（[engine/signals.lua](../engine/signals.lua)）。按内置默认参数跑出来的信号会被记下来：
信号日、信号日收盘、**加入时间**和加入时的收盘价，之后每次扫描顺手更新最新收盘，读取时算
「信号日以来」和「加入以来」的涨幅。两个价格都留，是因为一次突破可能晚几天才被发现（服务没开、
窗口是几天）：前者是规则本身的结果，后者是照着这张单子去做能拿到的。这是唯一诚实的检验——
规则没见过的未来。改过参数的扫描只显示、不记录：两条规则混在一张单子里就什么也说明不了；
同样的理由，旧定义下记的条目在升级后第一次启动时被丢弃。
同一只股票同一个信号日只记一次；按信号日保留 `SIGNALS_KEEP_DAYS`（180）天。

**参数怎么试。** `backtest.sweep`（单只）和 `strategy.sweep`（一组）跑参数网格：
均线窗口 × 上穿时高出的幅度 × 横盘振幅上限（默认 5 × 5 × 5），每格给出触发次数、胜率、收益分布和止盈止损命中。排名规则：

- `objective` 决定按什么排（中位数收益、平均收益或胜率，默认中位数）；
- `min_entries`、`min_win_rate`、`max_worst`、`max_sl` 是约束——**「保证不亏损」在这里的含义就是你设的约束**，
  它是对过去的筛选，不是对未来的承诺；
- 最优格旁边一定给出**邻居几格的表现**：跑一百多组参数，总有一组碰巧好看，邻居也好才说明是一片高地；
- 每次都给**基准**（同样这些股票、同一窗口里随便哪天买）。跑不赢基准的参数，再好看也没有意义。

**多只股票一起拟合**，而不是一只一只看：一只票的历史只是一条路径，在上面挑参数是在拟合噪声。
汇总也不是多次独立实验——同一波行情会让很多股票同时出信号，样本数看着大，信息量没那么大。

**股票范围**。`codes` 给定几只；`universe=screen` 按条件筛（ROE、PE、市值、行业…）；
`universe=market` 是全市场每一只——快照里有 5500 多只，去掉 ST 约 5360 只，
上限 6000，`bars_days` 控制每只留多少个交易日。扫描只需要几个月，但**回测要够长**：
400 天全市场约 320 MB，只覆盖一段行情；1200 天约 1 GB，才够逐年比较。

**分组归因**（`strategy.attribute`）问的是「这条规则在哪些行业、板块、地域更有效」。
这个问题很容易被答错：按行业分组、按收益排序，排在前面的只会是这五年本来就涨的行业——
半导体涨了，所以半导体里的信号也赚钱，和信号本身有没有用无关。

所以**每一组都和它自己的基准比**：同样这些股票、同一窗口、随便哪天买，报告的是两者之差。
并且因为一次要问一百多个组同样的问题，汇总行会写明**有多少组跑赢了自己的基准**——
接近一半就说明这张表是按运气排序的噪声。地域来自东方财富的 31 个地域板块（`groups.regions`，缓存 30 天）。

收益分布用直方图累计（0.5% 一档）而不是把几百万个收益率都存下来，中位数精度 0.5% 足够。

**扫描**（`strategy.scan`）用同一套规则判断「最近谁从横盘里上穿了均线」，每只股票只留最近的一次。
它只回答价格从平台上走出来了，不回答这家公司值不值得买——那是财报、估值和检查清单的事。

## 回测验证

实现在 [engine/backtest.lua](../engine/backtest.lua)。回放的是**引擎自己的规则**，
不是大模型的话，也不是某个故事：

| 信号 | 条件 |
|---|---|
| `value` | 锚指标 ≤ 它自己历史的第 25 百分位（阈值可调） |
| `trend` | 收盘 > MA5 > MA10 > MA20 > MA60（多头排列） |
| `value_trend` | 两个同时成立 |
| `band` | 锚指标 ≤ 你设置的区间下沿 |

**没有未来函数。** 第 t 天的分位只用第 t 天之前的数据算（扩张窗口），而且当天的值是在比较之后
才进入窗口的，不会参与定义自己的阈值。窗口不足 240 个交易日之前不出信号。
历史估值用的是数据源当天发布的值，不是拿今天的财报回算过去——后者会把事后的财报修订倒灌进历史。

**冷却期。** 两次信号之间至少间隔 `BACKTEST_COOLDOWN`（默认 20 个交易日）。
否则一个持续一个月的条件会被记成二十次信号，所有统计都变成同一段行情重复二十遍。

**方向胜率。** 从信号当天收盘买入，持有 20 / 60 / 120 / 250 个交易日后的收益率；
胜率是其中为正的比例。后面数据不足的信号在那个周期里不计入（`n` 会变小，而不是悄悄补零）。

**止盈止损命中率。** 从信号次日开始逐日用当天的最高价和最低价判断：先触及 +20%（止盈）
还是先触及 −10%（止损），最多看 250 个交易日。**同一天两边都触及时按止损计**——
日线看不出谁先到，算成赢是那种让所有回测都好看的假设。命中率 = 止盈次数 /（止盈 + 止损）。

**基准。** 同一段窗口里「随便哪天买」的同样统计。这一列不是装饰：一只四年涨三倍的股票，
随便哪天买的胜率都很高，信号的胜率没有明显高过基准就说明这条规则什么也没加。

**它不能告诉你什么。** 一只股票的历史只是一条路径，同一段行情里的多次信号不是多次独立实验；
胜率是对这条路径的描述，不是下一次的概率。不含交易成本、滑点、停牌；价格用前复权。

## 两个行情来源

日线有两个来源，缓存里记着是谁填的（`source`），**不会把两边的数据接在一起**：

| | 东方财富（`em`） | 通达信（`tdx`） |
|---|---|---|
| 形式 | HTTPS + JSON，每只约 500 KB | 自有二进制协议，长连接，每只约 14 KB |
| 复权 | 数据源已经前复权 | 原始价格，**由 xmoat 自己前复权**（见下） |
| 换手率 | 有 | **没有**（所以没有筹码分布） |
| 并发 | 连抓二十多只就开始掐连接 | 默认 32 条连接并行（分摊到多台服务器），实测 1000 只 14.5 秒、零失败 |
| 用在哪 | 自选股（技术面要换手率）、复盘的指数 | 全市场扫描与参数拟合；东方财富拒绝时的备用 |

**东方财富拒绝时改用通达信。** 东方财富的行情服务器会整段时间封一个地址（每个请求 160 毫秒内被掐断，
换域名、换 http 都一样），而其他接口照常。那样的一天如果只是记一条日志，检查就会拿上周的 K 线判断今天。
所以东方财富日线失败时同一次刷新改问通达信，缓存记成 `tdx`：当天没有筹码分布（技术面的 `chips_note`
会说明原因），下次刷新仍然先问东方财富，它恢复后整段重取回来。反过来不做：通达信断了就改走东方财富，
一次扫描就是几百个连续请求，正是会被封的那种用法。

指数也一样。通达信用同一个请求给指数日线，但每行多 4 个字节（当天上涨、下跌的成分股数），成交量以百手计；
而且代码本身说不清市场（000001 在上海是上证指数，在深圳是平安银行），所以市场取自证券本身。
实测 1200 个交易日与东方财富对比：沪深300 收盘价最大差 0.0002%，成交量换算后一致。

**自己做的前复权。** 通达信把原始价格和除权除息记录分开给，所以复权在
[engine/source_tdx.lua](../engine/source_tdx.lua) 里做，用的是通用公式（都按每 10 股计）：

    复权前价格 = (价格 − 分红/10 + 配股价 × 配股/10) ÷ (1 + (送股 + 配股)/10)

对每个除权日之前的全部 K 线生效，从最近的事件往回算。成交量不动——股数不是价格。
**验证过**：600519 的 1200 个交易日，自己复权的收盘价和东方财富的前复权相比，平均差 0.0036%、最大 0.007%，
就是四舍五入的差别。

协议细节（帧格式、价格的变长编码、通达信自己的浮点数）写在
[engine/tdx.lua](../engine/tdx.lua) 开头，解码器用录下来的真实响应做测试。

## 交易日历

实现在 [engine/calendar.lua](../engine/calendar.lua)。**没有节假日表**——写死一张表今年对、明年就错，而且没人记得更新。
它回答的是另一个问题：**现在有没有可能出现新数据**。

- 某一天的日线只可能在那天收盘之后出现，所以在「已有最后一根 K 线之后的下一个收盘」之前，不去抓；
- 周末是确定的，直接跳过；
- 节假日是**试出来**的：那天收盘后第一次去抓，发现最后一天没变，这个结果本身就把下次检查推到再下一天。
  一个长假因此只花一次请求，而不是每三小时一次。

收盘时间取 15:10（北京时间，按 `SCHEDULE_UTC_OFFSET` 换算）——15:00 收盘，数据源还要几分钟才把当天这根 K 线定下来。
当天这根 K 线在盘中是会动的，所以「最后一天就是今天且还没收盘」时，仍然按缓存时效（`QUOTE_TTL_MIN`）判断；
盘中抓到的那根算临时的，收盘后会再抓一次定稿。

**真正交易过的日子**不是推出来的：缓存的指数日线里有哪些日期，就是交易所开过门的哪些天。
`calendar_is_trading_day` 对范围内的日期给 true/false，范围外给"不知道"，不拿星期几冒充日历。
行情、板块表都走这套判断，`system.info` 里能看到它知道什么。

## 复盘与 regime

实现在 [engine/review.lua](../engine/review.lua)。复盘分三段，顺序就是问题出现的顺序：
**大盘 → 结构 → 自选**。前两段是描述，不含判断；第三段只是把分析对象里已有的结论，对每只自选股说一遍。

**指数。** 默认看上证指数、深证成指、创业板指、沪深300（`REVIEW_INDEXES`），
数据和个股走同一套日线缓存，指标也和技术面同一套（分位、距高点、量能）。

**Regime。** 在 `REVIEW_REGIME_INDEX`（默认沪深300）上算，只有三种状态：

| 状态 | 条件 |
|---|---|
| 多头 bull | 收盘 > MA250，且 MA250 近 60 个交易日上行，且收盘 > MA60 |
| 空头 bear | 收盘 < MA250，且 MA250 近 60 个交易日下行 |
| 震荡 range | 其余全部 |

不足 250 个交易日是 `unknown`。同时给出距 250 日高点的回撤和近 20 日年化波动率
（20 个日收益率的标准差 × √250）。

**这个规则是故意做粗的。** 更细的规则能更好地拟合过去，对明天却说不了更多。它的用处是给阅读提供背景
——「下跌市里的便宜」和「上涨市里的便宜」不是一回事——而不是择时。
`stance` 把三种状态机械地映射成一个仓位区间，输出里也写着它不是建议、不含预测。

**板块。** 东方财富的行业板块表（`push2` 行情接口，一页 100 条，分页取全部约 496 个）。
领涨、领跌各取前若干个；板块表缓存 `REVIEW_SECTOR_TTL_MIN` 分钟。

**涨跌家数按板块口径。** 这里数的是「多少个板块涨了」，不是「多少只股票涨了」：
东方财富的细分行业互相重叠，同一家公司会出现在多个板块里，把各板块的涨跌家数相加会重复计算
（实测约 1.6 万，而 A 股只有五千多家）。逐只统计需要几十次请求，不值当，所以这里明确用板块口径。

**自选段的提示** 来自点位：收盘价 ≤ 买入区间上沿是「已进入买入区间」，≤ 止损价是「跌破止损价」，
≥ 目标价是「达到目标价」。全部读本地缓存，复盘本身不刷新自选数据——那是定时检查的事。

## 全市场筛选

自选回答"我关注的这些怎么样"，筛选回答另一个问题："先看哪些"。它用的是另一份数据：全市场快照，
两张表按代码合并——当日估值和最近一个**年报**的业绩。

用年报而不是最近一期，是因为每家公司都有同一期年报，横向比较才成立；中报的 ROE 也不是年化的。

筛选**做不到**三件事，原因都一样：

- **没有股息率**：没有覆盖全市场的分红表可以合并。
- **没有估值分位**：分位需要每只股票自己的历史，那是 5500 次抓取而不是一次。
- **没有检查清单**：它要逐只读资产负债表。

所以筛选只负责缩小范围。一只股票是不是真的便宜、有没有雷，仍然要进个股页看它自己的历史分位和检查清单。

**利润含金量的替代指标**：全市场表里没有现金流量表，但有每股经营现金流和每股收益，所以筛选提供
`每股经营现金流 / 每股收益`。每股收益为负时这个比值没有意义，不参与筛选。

## 提醒规则

提醒来自比较同一只自选股刷新前后的两份数据（[engine/events.lua](../engine/events.lua)）。
两边用同一份自选设置做分析，所以在两次刷新之间修改合理区间，不会被当成价格穿过了区间。
第一次抓取没有可比较的数据，不产生提醒。

| 类型 | 触发条件 |
|---|---|
| 财报 | 出现了之前没有的报告期。季报、中报的营收和利润标注为"累计" |
| 分红 | 出现了之前没有的"报告期 + 方案进度"组合，且有现金分红金额：董事会预案、股东大会通过、实施分配各提醒一次 |
| 你的区间 | 估值相对你设的区间的位置变了：低于 / 位于 / 高于 |
| 估值分位 | 全部历史分位从 ≥ 下限跌到 < 下限，或从 ≤ 上限升到 > 上限（默认 10% / 90%）。一般企业看 PE（TTM），银行看 PB。只在进入区域时提醒，一直处在区域里不重复提醒 |
| 检查清单 | 某项检查从"通过"变成"注意"，或反过来。"数据不足"的变化不提醒 |
| 点位（仅持仓） | 收盘价进入某个点位区域：跌破止损价 / 跌进买入区间 / 涨到目标价。止损优先——价格同时在买入区间和止损之下时，说的是该走，不是该买 |
| 均线（仅持仓） | 均线排列从别的状态变成多头排列或空头排列 |

**点位和均线提醒需要先登记持仓**（自选项的 `position`，网页个股页「持仓」格子里填）。
只看不持有的股票，价格提醒是噪音：看到了也没有要做的事，而且行情一动就来一条；
持有的股票正相反，跌破止损是最值得让手机响一声的那条消息。没有登记持仓时，这两类提醒根本不会产生。

比较两边时，旧的那一份只能看到它自己那天为止的行情——否则会拿昨天的收盘价去比今天的均线，
凭空造出没发生过的穿越。「那天」是它当时**实际判断用的最后一根 K 线**（记录里的 `quotes_as_of`），
通常就是估值日；但那次刷新两个行情源都没取到时，它是按更早的 K 线判断的。如果仍按估值日截，
下一次会把当天发生的穿越当成早已知道的状态，永远不提醒。

每条提醒的 id 由股票和变化内容（报告期、方案进度、穿越发生的估值日期）决定，同一变化只记一次。

**推送。** 一次推送把所有待推送的提醒合成一条消息，按股票分组，最多列 20 条。至少一个渠道成功就算已推送；
所有渠道都失败时保留待推送，失败 3 次后放弃。推送时没有配置任何渠道，这些提醒标记为"未配置推送"，
以后配置了渠道也不会补发，避免一次收到几个月的旧提醒。

**内置规则的新突破随检查一起推送。** 每个交易日收盘后的检查会用默认参数把全市场跑一遍
（`SIGNALS_DAILY`，看最近 `SIGNALS_DAYS` 个交易日），新记入的信号放进同一条消息，**只推新加入的**：
每条有自己的「已推送」标记，和提醒一样，推出去一次就不再带。一天可能有几十只，
所以只列 `SIGNALS_PUSH_MAX`（10）只，按 ROE 从高到低，其余报个数；网页上用默认参数扫描发现的新突破也会推送。

**收盘复盘随推送一起发。** `PUSH_REVIEW` 控制：`digest`（默认）只在本来就要发的那条消息尾部附上复盘摘要；
`always` 每次检查都发，哪怕什么都没变；`off` 不发。默认是 digest——每个交易日一条例行播报，
正是这个工具一开始就不想成为的东西。摘要只有几行（指数、regime、板块涨跌、触及点位的持仓股），
因为企业微信应用消息连同提醒一共只有 2000 字节。

**没取到的数据也会推送。** 一次检查里，自选股刷新失败、东方财富和通达信都没给出日线、
复盘里的指数只能用缓存，都会列在消息里（「这次检查有数据没取到」），哪怕当天没有任何提醒：
一次没能看全的检查和一次什么都没发生的检查，结果同样是「0 条提醒」，不说出来就分不清。
这部分放在复盘摘要之前，消息超长被截断时先丢复盘；每条原因截到 150 字节。
复盘里用缓存顶上的指数会标出它是哪天的数据（「未更新」）。

**定时检查。** 默认北京时间工作日 17:30，按 UTC 偏移计算，与服务器所在时区无关。每个时间点每天最多运行一次，
记录在 `data/state.json`；服务在当天错过的时间点之后启动，会补跑一次。节假日无法识别，但那天数据没有变化，不会产生提醒。

## 大模型解读

可选功能，需要配置模型。它读的是**已经算好的事实**和**公司自己写的经营评述**，不碰原始数据。

**给模型什么。** [engine/insight.lua](../engine/insight.lua) 把分析对象渲染成一段事实文本：估值和分位、
经营质量的逐年序列和汇总、主营构成及占比变化、分红、检查清单的每一条结论，再加上经营范围和最近两期经营评述。
和网页上看到的是同一批数字。

**要求模型做什么。** 系统提示明确：只依据事实作答；不要自己计算、估算或换算任何数字；引用数字时照抄；
事实里没有依据就写"无法判断"；经营评述是公司的自我陈述，引用时要说明；不给买卖建议。
输出是固定结构的 JSON：总体判断、护城河来源与强度、证据、变化、风险、值得核实的问题。
Claude 用 `output_config.format` 的 JSON Schema 强制结构；OpenAI 兼容接口只能要求 JSON 模式，结构由程序再检查一遍。

**不需要相信上一条。** 回答里的每个数字都会被抽出来和事实文本比对，找不到的列在 `unverified` 里，界面上标红提示。
比对规则：按回答自己写的精度四舍五入后匹配（事实里的 32.56% 写成 32.6% 算通过，写成 35.6% 不通过）；
年份和不带单位的小整数（"3 项""5 年"）不参与核对。

**什么时候会自动调用。** 默认只有一种情况：定时检查发现某只自选股发布了**年报**，会为它生成一次解读，
并随当次提醒一起推送（`INSIGHT_ON_ANNUAL_REPORT=0` 可关闭）。其余时候都要手动点"生成解读"或提问。

**费用。** 每次解读或提问都是一次模型调用。一次解读的输入大约 4 千汉字。Claude 的请求默认带
`fallbacks: "default"`：被安全分类器拒绝时，服务端自动换模型重跑，不会直接失败。
